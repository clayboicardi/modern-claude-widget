### P2 — Behavior changes between API 37 and today that touch this app (info)

Checked against the Android 17 [targeting-37](https://developer.android.com/about/versions/17/behavior-changes-17)
and [all-apps](https://developer.android.com/about/versions/17/behavior-changes-all) lists, the
QPR1/QPR2/QPR3 release notes and the [37.2 API diff](https://developer.android.com/sdk/api_diff/37.2/changes).

| Area | Change | Applies | Effect here |
|---|---|---|---|
| App widgets | `RemoteViews` updates over `6 × width × height` bytes of bitmap throw `IllegalArgumentException` | target 37 | None. The widget sends no bitmaps: backgrounds, glyphs and the logo are resource IDs (`ImageProvider(resId)`). |
| Background activity launch | BAL protections extended to `IntentSender`; legacy `MODE_BACKGROUND_ACTIVITY_START_ALLOWED` to be replaced | target 37 | None from this change: the app never sends a `PendingIntent` or `IntentSender`; the launcher does. Background-launch rules did break v1.0 for a different reason. See P3. |
| Broadcasts | 17 QPR2 stops self-broadcasts raising process importance | all apps | None. The change excludes broadcasts sent on another app's behalf through a `PendingIntent`, which is what a v1.0 tap was; since P3 a tap is not a broadcast at all. |
| Safer intents | Android 16 strict intent matching is opt-in by the receiving app | n/a | None. `ACTION_VIEW claude://…` + `setPackage` is an implicit intent resolved by filter, so it already complies. |
| Package visibility | Unchanged. "`startActivity()` doesn't require package visibility" ([use cases](https://developer.android.com/training/package-visibility/use-cases)) | all apps | Two of the three `<queries>` entries are unnecessary. See C3. |
| `FLAG_ACTIVITY_CLEAR_TASK`, exported receivers, widget picker | Nothing found in the 17.0, 37.1 or 37.2 notes | — | None. |
| Force-stop | Since Android 15, force-stopping an app greys out its widgets until the app is next launched ([Android 15 all-apps](https://developer.android.com/about/versions/15/behavior-changes-all)) | all apps | This app has no launcher activity the user could open. Checked on the emulator: see section 6. |

Platform source for 37.1, 37.2 and QPR3 is not in public AOSP, so for those levels this rests
on Google's release notes plus the device test, not on source.

### P3 — Taps were blocked as background launches in Kvaesitso (high, fixed)

This section was first written on 2026-11-24 as "the callback path works, keep it". The
phone probe two days later showed that was wrong. What follows is the corrected account.

- **How v1.0 launched.** Glance's `actionRunCallback` is a broadcast `PendingIntent` to its
  non-exported `ActionCallbackBroadcastReceiver`, which runs `onAction` under `goAsync`
  (confirmed in the 1.1.1 and 1.2.0 AAR bytecode). The app then called `startActivity` from
  that broadcast. Starting an activity from a broadcast is a background activity launch
  (BAL), which Android allows only if the sender passes its own allowance along with the
  `PendingIntent`
  ([secure-bal](https://developer.android.com/guide/components/activities/secure-bal)).
- **Evidence.** From the Pixel launcher on both emulators the launch was allowed
  (`BAL_ALLOW_TOKEN`). From Kvaesitso 1.41.0, on the phone and on the API 37.2 emulator, it
  was refused: `Background activity launch blocked! … callingUidProcState: RECEIVER …
  (BAL_BLOCK) result code=102`, and the launcher stayed in front. So on Clay's phone every
  tap did nothing. Why the Pixel launcher's taps carry the allowance and Kvaesitso's stock
  `AppWidgetHostView` taps do not was **not established**.
- **Fix (commit `ba22f34`).** A tap now starts `LaunchActivity` with Glance's
  `actionStartActivity`, which is the path the
  [Glance guide](https://developer.android.com/develop/ui/compose/glance/user-interaction)
  recommends. `LaunchActivity` is not exported, uses `Theme.NoDisplay`, runs the same ordered
  chain (`ClaudeLauncher`) and finishes in `onCreate`. Because the launcher's visible window
  starts it, the system allows it (`BAL_ALLOW_VISIBLE_WINDOW [realCaller]`), and an activity
  the user just opened may start others. The ordered fallback is kept, which was the reason
  the 24th's version of this section gave for staying on the callback.
- **Verified.** Kvaesitso on the phone with the real Claude app (R2); Kvaesitso on the
  API 37.2 emulator; the Pixel launcher on the API 37.0 emulator (section 6).
- **Still true: a blocked launch is silent.** The system gives no exception and no return
  value, only a logcat line. The fallback chain catches "no handler" and `SecurityException`;
  it cannot catch a BAL block. That is stated in the code and is why launches are verified on
  a device, in every launcher that matters, not only in tests.
- **No longer applies: vivo on Android 12–14.** Glance 1.2.0 runs *callbacks* in a WorkManager
  worker on those devices (`maybeLaunchAsyncRequestWorker`), which was a risk for the old
  path. The widget no longer uses a callback. The new path is untested on vivo hardware, like
  every other non-Pixel device.

## 4. Code

### C1 — A refused Play Store launch skipped the web fallback (medium, fixed)

- **Evidence.** `start()` caught only `ActivityNotFoundException`; `SecurityException` was
  caught around the whole attempt. If the `market://` launch threw `SecurityException`, the
  https fallback in the same attempt never ran. A new test reproduced it (red), then passed
  after the fix (green).
- **Done.** Each start handles both exceptions itself.

### C2 — Launch path and intent security (info)

Reviewed against the `android-intent-security` skill.

- No Intent is ever received and forwarded: every Intent is built from the in-app registry,
  keyed by a string id. An unknown or missing id fails closed to "open Claude".
- Deep links are pinned with `setPackage("com.anthropic.claude")`, carry no extras and no
  URI-grant flags (asserted in tests), so another app registering `claude://` cannot
  intercept a tap.
- The app creates no `PendingIntent` itself; Glance creates them (immutable, explicit).
- `LaunchActivity` (added on 2026-11-26, see P3) is not exported, so only the widget's own
  `PendingIntent` can start it. It reads one string extra, the destination id, and looks it
  up in the registry like before; a test sends it a hostile extra and checks nothing from it
  is forwarded. It stays out of the app drawer and out of recents.
- The only unguarded exported component is the widget receiver, which must be exported.
  Everything else exported comes from libraries and is permission-guarded
  (`BIND_REMOTEVIEWS`, `BIND_JOB_SERVICE`, `DUMP`). Pinned by `ManifestContractTest`.
- **Merged-manifest permissions.** The app's manifest requests nothing, but Glance pulls in
  WorkManager, which adds `WAKE_LOCK`, `ACCESS_NETWORK_STATE`, `RECEIVE_BOOT_COMPLETED` and
  `FOREGROUND_SERVICE`. There is **no `INTERNET`**, so the README promise holds. The exact
  set is now asserted in a test so a dependency bump can't change it unnoticed.

### C3 — `<queries>` declared more than the app needs (low, fixed)

- **Evidence.** The manifest declared `com.android.vending` and *every https VIEW handler*
  visible, with a comment saying the Play Store fallback needed them. It doesn't:
  `startActivity` never requires package visibility; only `getLaunchIntentForPackage` (a
  query) does. Declaring all https handlers made every installed browser visible to the app.
- **Done.** Only `com.anthropic.claude` is declared. Verified on both emulators: the
  `market://` and https fallbacks still start (section 6).

### C4 — Hint text wrapped and was cut off at the smallest size with large fonts (medium, fixed)

- **Evidence.** API 37 emulator, widget resized to 2 cells wide, system font at 200%:
  "Ask Claude…" wrapped to two lines inside the fixed 48dp pill and the second line was
  clipped.
- **Done.** `maxLines = 1` on the hint and the button labels. Same setup now shows one line
  ("Ask Cla…"); at 100% font the full text fits.

### C5 — Loading placeholder was a grey square (low, fixed)

- **Evidence.** `widget_loading.xml` painted a flat `#1F1F1F` rectangle with square corners,
  shown from placement until Glance's first render (also lint's Overdraw warning).
- **Done.** It uses the widget's own rounded shell drawable. Seen working on the 37.2
  emulator, where an experimental build that failed to render sat on the placeholder: it
  looked like an empty widget shell, not a grey box.

### C6 — Buttons were named twice for screen readers (low, fixed)

- **Evidence.** With labels visible, each button's icon carried the same content
  description as its text label. The emulator's accessibility tree showed both a
  `desc='Chat'` node and a `text='Chat'` node inside one click target, which a screen reader
  announces as "Chat, Chat". Not checked with TalkBack itself (not installed on the emulator
  image).
- **Done.** The icon is decorative next to a label and keeps its description when it is the
  whole button. One existing test assertion encoded the duplication and was changed; the
  commit message says so.

### C7 — Dead code and stale comments (low, fixed / noted)

- **Fixed.** Unused colors `ink_600` and `brand_purple`; a `testInstrumentationRunner` with
  no instrumented tests; comments pointing at a file and a drawable that don't exist, and
  at "below Android 12" paths that can't run with minSdk 31.
- **Left as is, on purpose.** `LaunchUri` (the `q=` encoder) is called only by its tests. The
  README documents it as the hook for a prefilled Code task, and Anthropic now documents that
  parameter, so it stays. `Destination.label`, `ClaudeAction.defaultLabel` and
  `RouteConfidence` are data nothing reads at runtime; harmless, and `RouteConfidence` is
  asserted in tests as documentation.
- **Strings exist twice.** "Ask Claude…", "Chat" and "Code" are literals in `ClaudeWidget.kt`
  and also in `strings.xml` (used by the picker preview). They match today. Unifying them
  needs a `Context` in the composable and a Robolectric-backed UI test; listed as a proposal.

### C8 — Glance update and memory behaviour (info)

Reviewed against the `glance-appwidget-updates-and-memory` skill.

- The widget is stateless: no `updateAppWidgetState`, no periodic work, `updatePeriodMillis=0`.
  Nothing can go stale.
- No bitmaps cross the IPC boundary. `dumpsys appwidget` on the emulator reports
  `views_bitmap_memory=0` for the widget, so the Android 17 memory cap cannot be hit.
- No callback class is left for Glance to create by reflection (taps start an activity, P3).
- `SizeMode.Exact` is what the `glance-canonical-layouts` skill mandates.
- No `onCompositionError` override: with no state and no bitmaps there is nothing a fallback
  layout would do differently.

### C9 — Widget sizing and the picker preview (info)

- Pixel launcher picker (API 37.0 and 37.2): listed as "Claude Widget", 4 × 2, preview
  matches the live widget. Kvaesitso's picker showed no preview at all until K1.
- Resizes down to 2 cells wide (icons only) and up to full width; minimum height 2 rows.
- The picker shows the app icon square inside a circle, which is lint's one remaining
  warning (`IconLauncherShape`). See proposals.

- **Fixed: a tap could now crash the app where v1.0 only logged.** Glance's callback
  receiver caught every exception; `LaunchActivity` did not, and the launch code caught only

- **Checked, no change: widgets placed under v1.0.** They hold click intents that name a

- **Answered, no change: the Glance-to-activity hand-off is only device-tested.** JVM tests

- **Left as a proposal: a tap is silent when nothing at all can be started** (no Claude, no

### T2 — CI workflow ran on a removed runtime (high, fixed)

- **Evidence.** `ci.yml` used `actions/checkout@v4`, `actions/setup-java@v4`,
  `android-actions/setup-android@v3` and `gradle/actions/setup-gradle@v4`. Those majors run
  on Node 20, which GitHub removed from Actions runners on 2026-09-23
  ([changelog](https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/)).
  CI last ran on 2026-06-23, and `ubuntu-latest` has since moved from 24.04 to 26.04. Whether
  the old workflow still passes on `main` was **not tested** (that would need a push to
  `main`); it is replaced rather than probed.
- **Done.**
  - `actions/checkout@v7`, `actions/setup-java@v6`, `android-actions/setup-android@v4`
    (latest majors, confirmed from each repo's releases).
  - Gradle caching now comes from `setup-java`'s `cache: gradle`. `gradle/actions` v6 moved
    its caching into a proprietary component and says upgrading accepts its
    [Terms of Use](https://gradle.com/legal/terms-of-use/). That acceptance is the repo
    owner's to give, so the workflow no longer uses that action. See proposals.
  - `permissions: contents: read`, a 20-minute timeout, and concurrency that cancels a
    superseded run on a pull request but never on `main`.
  - Lint and test reports are uploaded as an artifact, including on failure.
  - The old `setup-gradle` step also validated the wrapper JAR. A small shell step now does
    that directly: it compares `gradle-wrapper.jar` with the SHA-256 Gradle publishes for the
    pinned version.
  - Robolectric's Android runtime (about 240 MB, fetched into `~/.m2` at test time) is cached
    with `actions/cache@v6`, so a run doesn't depend on a fresh Maven Central download.
- **Verified.** PR #1's run on `ubuntu-26.04`: BUILD SUCCESSFUL in 2 m 51 s, no annotations,
  reports artifact uploaded.

## 8. Kvaesitso (Clay's launcher)

Source: [MM2-0/Kvaesitso](https://github.com/MM2-0/Kvaesitso) at commit `1a14e9b`
(2026-11-24; latest release v1.41.0). First read from source, then run: v1.41.0 on the
API 37.2 emulator (release APK from the project's GitHub releases, SHA-256 matched the
published digest) and on the phone, where it is the default launcher.

How it hosts third-party widgets (`app/ui/.../widgets/external/AppWidgetHost.kt`,
`.../sheets/WidgetPickerSheet.kt`, `.../sheets/ConfigureWidgetSheet.kt`,
`data/widgets/.../AppWidget.kt`):

- A stock `android.appwidget.AppWidgetHost` and its default `AppWidgetHostView`. No custom
  click handling.
- On API 31+ it reports one size to the widget: the dp size of the box it lays the widget
  out in. It then adds its own 8dp padding inside that box unless "Borderless" is on.
- Per-widget settings, with their defaults: **Borderless** off, **Background card** on,
  theme colors on.

### K1 — The widget showed no preview in Kvaesitso's picker (medium, fixed)

- **Evidence.** `WidgetPickerSheet.kt` calls `loadPreviewImage(...)` and shows the result;
  when it is null the row is just a 24dp icon, the label and the description. It never
  inflates `previewLayout`. This widget declared only `previewLayout`.
- **Done.** `android:previewImage` added next to the `previewLayout`
  (`res/drawable-nodpi/widget_preview_image.png`, 914 × 507, about 98 KB). The stock
  launcher keeps using the layout; Kvaesitso and other launchers that only load the image
  get the image. Seen in the running Kvaesitso picker on the emulator. The earlier comment
  in `claude_widget_info.xml` ("No previewImage: that is only the pre-Android-12 fallback")
  was wrong and is replaced.
- **The image is a screenshot in the repo.** It is the real widget at 4 × 2, captured on the
  API 37.2 emulator and cropped to the widget alone, corners masked to the 28dp shell. It
  shows nothing but the widget. It must be regenerated when the look changes (DESIGN.md).

### K2 — Default placement in Kvaesitso is a narrow widget inside a card (low, documented)

- **Evidence.** On add, Kvaesitso sets width = the provider's `minWidth` (250dp) and height =
  `minHeight` (168dp), centred in a full-width card, with 8dp padding. So by default the
  widget's own rounded shell sits inside Kvaesitso's card, 250dp wide. Resizing honours
  `minResizeWidth`/`minResizeHeight` (180 × 140dp) and allows any height up to 2000dp.
- **Effect on layout.** Glance is told 250 × 168dp, so labels show. The real drawing area
  is 16dp smaller each way because of the padding. At Kvaesitso's minimum width the hint has
  about 78dp and shortens to "Ask Clau…"; before the one-line fix (C4) it would have wrapped
  and been cut off there at normal font size.
- **Done.** Default placement confirmed on the emulator. README and DESIGN now say: in
  Kvaesitso, resize the widget to full width, turn **Borderless** on and **Background card**
  off to get the intended look. The widget can't set these itself.

### K3 — Taps did nothing in Kvaesitso (high, fixed)

- **What was expected.** From reading the source: Kvaesitso uses the stock host view, so
  taps should behave as on the stock launcher. That reasoning was wrong.
- **What happened.** On the phone and on the emulator, v1.0's taps were blocked as
  background launches from Kvaesitso and allowed from the Pixel launcher. Details and the
  fix are in P3. June's "confirmed end-to-end via the widget" did not record which launcher
  was used, so it is not known when this broke or whether it ever worked in Kvaesitso.
- **Lesson kept in `CLAUDE.md`.** Tap the widget in every launcher that matters. Reading a
  launcher's source did not predict this.

## Proposals (not done — each needs a decision)

1. **Release minification — big win, but not a one-line switch.** *Real trade-off.*
   The release APK is 17.8 MB unminified and 0.65 MB with R8 + resource shrinking. But that
   build **crashes on startup** (`Failed to create an instance of
   androidx.work.impl.WorkDatabase`): Glance depends on WorkManager 2.7.1, whose Room
   database class R8 strips. With an added
   `-keep class * extends androidx.room.RoomDatabase { <init>(); }` it is 1.46 MB and no
   longer crashes, but on the API 37.2 emulator the widget then **stayed on its loading
   placeholder** and never rendered. So more keep rules are needed, and each must be
   verified on a device. Not finished here. It also only matters once releases are signed:
   v1.0.0 shipped the debug APK (19.4 MB then, 22.2 MB now), because there is no release
   keystore. Doing this properly = a signing setup (yours to create), the right keep rules
   (or an explicit newer `androidx.work` dependency), `assembleRelease` in CI, and an
   on-device check of the minified build.
2. **Chat route durability.** *Partly resolved; the rest is a real trade-off.* The probe
   showed the risk is real: `claude://new` changed destination between June and November
   without failing. Chat now uses `claude://claude.ai/new`, the form Anthropic documents
   (for Desktop). It is still not documented for mobile, so it can change again the same
   way, and the fallback chain cannot notice. Options: (a) re-run the probe after Claude
   updates that touch navigation, which is what `CLAUDE.md` describes; (b) switch Chat to
   `https://claude.ai/new`, the web app's own URL, which is the least likely to be removed,
   after confirming on the phone that it opens the chat composer (it opened *a* composer;
   the screenshot was not inspected). Not done here because (b) is unverified.
3. **Prefilled Code task button.** `claude://code/new?q=…` (with `mode`, `repo`, `branch`) is
   now officially documented. A third button or a configurable prompt is a new feature.
4. **Adaptive app icon.** *Coin flip.* The icon is a full-bleed square PNG, which launchers
   crop into their mask shape (lint `IconLauncherShape`). An adaptive icon (foreground +
   background layers) from the same CC artwork would fix it; it needs new artwork exports.
   Related: the logo inside the pill has an opaque black square behind it.
5. **Single source for the three label strings** (C7). Small refactor plus a Robolectric UI
   test. Worth doing if the widget is ever translated.
6. **`gradle/actions` v6 caching.** If you accept Gradle's Terms of Use for its caching
   component, CI could return to `setup-gradle`, which also validates the wrapper JAR.
   Functionally optional: the build is 3 minutes and the wrapper distribution is
   checksum-pinned.
7. **`android:allowBackup="false"`.** The app holds no user data; Glance's internal state is
   meaningless on another device. Harmless either way.
8. **Pin GitHub Actions to commit SHAs.** Stronger supply-chain posture than version tags
   for a public repo; costs manual updates.
9. **`CLAUDE.md` in a public repo.** It names your phone and one machine's quirks. Nothing
   in it is secret. If you'd rather not publish that, the personal parts can move to an
   untracked `CLAUDE.local.md`.
10. **Drop `CLEAR_TASK` from the deep-link launch.** *Real trade-off.* It was added in June
   because a running Claude ignored links without it. Claude `1.261123.19` follows a link
   sent with `NEW_TASK` alone (R2). Keeping it: each button gives the same result every
   time, and it is the one combination verified on both app generations, but it throws away
   whatever Claude was showing (a half-typed message, a scrolled session). Dropping it:
   Claude keeps its task, but someone still on an older Claude build gets a button that
   only brings Claude to the front. Kept for now; if dropped, re-probe warm and cold.
11. **A second pair of eyes on other launchers.** P3 was invisible on the Pixel launcher and
   total on Kvaesitso. The new path is the standard one and should hold elsewhere, but only
   those two launchers were tested. Worth a tap test on any other launcher you use, and on
   a non-Pixel phone if one is ever at hand (the old vivo-specific risk is gone, see P3).
12. **Say something when nothing can be opened.** *Coin flip.* If Claude, the Play Store and
   a browser are all missing, a tap does nothing and says nothing. Now that a tap runs in an
   activity, a one-line toast ("Claude isn't installed") is possible. It is new UI and a new
   string, and the situation barely exists on real phones.
